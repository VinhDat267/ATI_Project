# FS-04 — Filesystem write approval and durable dispatch guard

**Status:** VERIFIED for the FS-04 checkpoint on 2026-09-14. The mutation is real MCP `write_file`; the PostgreSQL row is only a committed dispatch reservation, never a receipt or proof that bytes reached disk.

## Delivered

- Added migration `0005_filesystem_dispatches.sql` and the Drizzle mapping. The marker is keyed by `operation_id`, owner/run bound, stores the relative path, UTF-8 content SHA-256, launch/artifact hash, and reservation timestamp.
- Added `reserveFilesystemDispatch` and `recheckFilesystemDispatch`. They require strict approval/operation/snapshot identity, owner and workflow-version binding, `run.claimed_by === worker.id`, live approval TTL checked by PostgreSQL, `non_idempotent` receiver mode, exact canonical args/payload hash, current composite gateway policy, and active worker lease.
- Existing markers fail closed with `FilesystemAlreadyDispatchedError`; they are never silently replayed or deleted. Other guard failures are before-dispatch failures and do not send an MCP packet.
- Wired a guard-owned database handle into the composite gateway. The controller worker capability remains authoritative for advisory-lock liveness; the guard store is used only for its transaction and never claims a second worker lease.
- Enabled public `filesystem.write_file` only after guard tests existed. The public catalog now has 10 tools: 8 task_hub + `read_file` + `write_file`; the upstream filesystem discovery still has 14 raw names and all unselected names remain unreachable.
- Added strict write acknowledgement normalization and bounded UTF-8 read-back. Raw errors, acknowledgement drift, and read-back drift stay uncertain after dispatch; filesystem calls never use the task_hub receipt table.
- Extended `reconcile` with `dispatch_marker: present|absent`, `receipt: not_supported`, current operation state, and `result: null` for filesystem operations.

## Deliberate boundary

FS-04 does not claim a filesystem receipt, atomic DB/filesystem commit, crash-after-write evidence, CLI two-server controller plans, or automatic recovery. Those are FS-05 concerns. After a raw dispatch has started, expiry/cancel cannot undo a filesystem mutation; the marker and `unknown` certainty preserve that ambiguity for reconciliation. No commit or staging was performed.
